# v0.9.5 — Specification Edition and Distribution Identity

{% include gaam-meta.html %}

**Release date:** 4 November 2026  
**Current Candidate distribution and test-suite release:** v0.9.5  
**Authoritative normative specification edition:** v0.9.0  
**Normative semantic baseline:** v0.9.0  
**Canonical artifact, profile and requirement identifier lineage:** v0.9.0  
**Normative change:** None

## Reason for the release

GAAM v0.9.4 was a valid maintenance distribution incorporating the unchanged v0.9.0 normative document. But the legacy `normativeVersion` Candidate-release field could be mistaken for the printed edition of that document. GAAM v0.9.5 provides a consistent version ontology, current publication entry point, citation rule and falsifiable metadata validation. It does **not** retroactively manufacture or publish a new v0.9.4 normative edition.

## Consumer-facing changes

- Add `release.json.specificationEdition = "0.9.0"` and `PROJECT-STATUS.yaml.project.specification_edition = "0.9.0"`; retain `version`, `candidateBaseline` and legacy `normativeVersion` at **0.9.5**. The latter two fields identify the Candidate **release**, not the normative-text edition.
- The stable [specification index](../specification/) now declares the authoritative current normative edition and the current distribution separately. The [publication guide](../docs/specification-publication.md) specifies edition, distribution, semantic-baseline and canonical-artifact change rules.
- A new source-to-publication validation check rejects a release that advertises an edition not printed in the authoritative normative text, a missing/changed historical permalink, mismatched stable index, incompatible legacy release metadata or divergent project status.
- Update the versioned portable conformance-tooling metadata and navigation while preserving the existing normative artifacts, independent E2/E3 evidence boundary and experimental v0.10.0 isolation.

## Compatibility and migration

There is **no normative migration**. The actual normative specification, v0.9.0 JSON Schema `$id` values, governed profile/requirement identifiers, conforming behaviour and v1 adapter request/response semantics remain unchanged. Existing consumers can ignore the newly added `specificationEdition` field; consumers selecting a normative text should use it instead of inferring edition from `normativeVersion`. Clients comparing informative result/kit release fields should expect **0.9.5**.

The historical v0.9.0 specification permalink and all older GitHub release tags/assets are retained. The edition model is prospective, not a reinterpretation or mutation of historical release contents.

## Reproduction and assurance

Run on the tagged checkout:

```bash
python -m pip install -r requirements-dev.txt
python scripts/version_identity.py
python -m pytest tests/test_version_identity.py -q
python scripts/validate.py
python -m pytest tests -q
```

The established Validate, Pages, canonical publication and release workflow checks must pass on the released commit. Source files, schema bytes, generated documents and distribution assets remain auditable under the existing publication controls.

This is a publication/metadata integrity correction, **not** independent implementation evidence, operational authorization, E2/E3 interoperability, certification or promotion of informative OAuth/MCP mappings and experimental v0.10.0 fields. The bounded delegated-agent gateway remains repository-controlled E1, with original source/authentication, scope and receipt limitations preserved.
