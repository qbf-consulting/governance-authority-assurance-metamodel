# v0.9.2 — Ecosystem Validation Evidence

{% include gaam-meta.html %}

**Release date:** 22 September 2026  
**Distribution/test-suite release:** v0.9.2  
**Normative baseline:** v0.9.2  
**Semantic/canonical artifact baseline:** v0.9.0  
**Release class:** Normative Candidate maintenance release  
**Normative-status designation:** 26 September 2026

GAAM v0.9.2 turns two ecosystem-facing reviews into executable validation evidence.

The release promotes the EUDI Wallet ARF v3.0.0 and GLEIF vLEI EGF v4.0 reviews from narrative architectural analysis into a paired implementation-validation workstream, then converts selected recurring findings into behavioural vectors that exercise existing GAAM v0.9.0 semantics.

The result is deliberately narrow: **v0.9.2 is the current normative Candidate implementation baseline while preserving the v0.9.0 normative semantics and frozen identifiers unchanged.**

## Why this release exists

The two validation cases stress GAAM from different architectural directions.

- **GLEIF vLEI EGF v4.0** acts as an **explicit-authority benchmark**. It exposes questions around delegated authority, role semantics, assurance scope, revocation dependencies and downstream reliance where governance artifacts are already comparatively machine-verifiable.
- **EUDI Wallet ARF v3.0.0** acts as a **distributed-authority benchmark**. It tests whether GAAM can reason about authority that is validly distributed across legislation, implementing acts, national governance, certification, registries / Trusted Lists and protocol state.

Using both cases together helps distinguish weaknesses in an external ecosystem mapping from weaknesses in GAAM itself. The two reviews are not treated as GAAM conformance assessments.

## What changed

### 1. Paired implementation-validation cases

The common ecosystem-crosswalk contract is now schema version **1.1** and records substantially richer implementation context for every finding, including:

- authority sources;
- governed actors;
- governed relationships;
- governed effects;
- enforcement mechanisms;
- revocation mechanisms;
- assurance mechanisms;
- what a source or relationship **establishes**;
- what it explicitly **does not establish**;
- expected evidence;
- candidate tests; and
- known limitations.

The existing readiness vocabulary remains:

`covered / partial / gap / not-applicable / unknown`

This vocabulary still describes framework-readiness observations. It is not a GAAM conformance scale.

### 2. Five ecosystem-derived behavioural vectors

v0.9.2 adds five executable vectors derived from recurring questions across the EUDI and vLEI cases.

#### `authority-role-out-of-scope-rejected`

A valid role, recognition record or status artifact must not be treated as authority for an effect that falls outside the represented authority scope.

This exercises the distinction between:

- identity / recognition;
- role;
- authority; and
- effect-specific permission.

#### `delegation-upstream-authority-revoked-rejected`

A dependent delegation cannot remain valid after the upstream authority on which it depends has become inactive or revoked.

This exercises dependency-aware authority and delegation semantics without introducing a new revocation model.

#### `runtime-unknown-authority-fail-closed-valid`

When authority state is stale or unknown, the safe runtime state is valid only where the effect is not admitted and the system fails closed.

This directly exercises GAAM's existing runtime-governance and observability semantics.

#### `assurance-stale-evidence-rejected`

Assurance evidence outside its validity window cannot support a current assurance claim, even when the evidence source or assessment independence would otherwise be sufficient.

This separates assurance provenance from assurance freshness.

#### `decision-unattributed-rejected`

A consequential decision record is insufficient where authority, policy, evidence and assurance may be present but no accountable party is attributable.

This reinforces the link between executable governance and accountability evidence.

## Requirement-level traceability

Every new behavioural vector is wired into `matrices/requirement-assurance-traceability.csv`.

The vectors therefore contribute to existing requirement assurance rather than forming an ungoverned parallel test suite.

The mappings touch existing GAAM areas including:

- authority scope;
- effect boundaries;
- relationship semantics;
- delegation lifecycle;
- runtime observability;
- assurance validity;
- evidence;
- trust decisions; and
- accountability.

No new normative requirement identifier is introduced by this release.

## Portable conformance tooling

The portable conformance-kit distribution identity advances to **v0.9.2**.

The portable result contract also advances to v0.9.2 while continuing to report:

- **releaseVersion:** 0.9.2
- **normativeVersion:** 0.9.2
- **semanticBaseline:** 0.9.0

That split is intentional. `normativeVersion` identifies the Candidate release an implementation or conformance result targets; `semanticBaseline` records the frozen semantic/canonical lineage retained from v0.9.0.

## Compatibility and normative stability

GAAM v0.9.2 is the current normative Candidate baseline. Its promotion changes the active release designation, not the underlying semantics. It does **not** change:

- the v0.9.0 normative text incorporated by v0.9.2;
- normative requirement semantics;
- profile identifiers;
- canonical schema identifiers;
- controlled-vocabulary semantics;
- conformance levels; or
- the canonical v0.9.0 schema namespace.

Existing artifacts that were valid against GAAM v0.9.0 remain semantically valid under the v0.9.2 normative Candidate baseline because no requirement, profile, vocabulary or canonical schema meaning changed.

Implementations should continue to use `gaamVersion: 0.9.0` where that field identifies the retained semantic/canonical artifact version. Release- and conformance-level metadata should identify `normativeVersion: 0.9.2` and `semanticBaseline: 0.9.0`.

The value `0.9.2` therefore identifies both the current normative Candidate release and the distribution, portable tooling state, behavioural test-suite state, release packaging and generated evidence.

## Release and validation pipeline

v0.9.2 is built through the repository's validated release workflow.

The release path:

1. accepts a trusted push to `main`;
2. waits for the full `Validate` workflow to pass for that exact commit SHA;
3. verifies `VERSION`, `release.json`, release notes, the v0.9.2 normative baseline and the preserved v0.9.0 semantic/canonical artifact baseline;
4. regenerates repository validation and package evidence;
5. builds a byte-reproducible source distribution using the declared release date;
6. publishes the Git tag and GitHub Release for `v0.9.2`;
7. attaches the release archive, release record, package manifest, checksums and validation report; and
8. explicitly marks the release as **Latest**.

The workflow treats an existing GitHub Release and its assets as historical, read-only release evidence on ordinary `main` pushes. The 26 September normative-status designation is therefore recorded through repository governance and current publication metadata without retagging v0.9.2 or replacing its originally published archive bytes.

## What this release does not claim

The EUDI and vLEI mappings are **implementation-validation cases**, not external certifications and not claims that either ecosystem conforms to GAAM.

The new vectors are repository-controlled behavioural evidence against existing GAAM semantics. They do not constitute:

- independent implementation evidence;
- independent interoperability evidence;
- certification;
- an L4 independent-assessment claim; or
- closure of GAAM's v1.0.0 candidate-exit gates.

## What comes next

The practical next step is to continue converting high-value crosswalk findings into executable evidence only where the existing normative model already supports a defensible test.

Where the two implementation cases expose a recurring concept that cannot be represented without changing GAAM semantics, that finding should remain an evidence-backed candidate for the governed research-to-normative promotion process rather than being added opportunistically to the validator.

This keeps the evolution path disciplined:

**external ecosystem observation → structured crosswalk → bounded test hypothesis → executable evidence → repeated implementation signal → governed normative proposal, if warranted.**
